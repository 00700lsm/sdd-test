# Research: 알림 창과 확인 창

## Decision: 기존 Java 21 + Spring Boot 4.1.1 화면만 바꾼다

**Rationale**: 이 기능은 검증, 권한, 상태 전이, 저장 결과를 바꾸지 않는다. 001에서 쓰는 서버 렌더링 Thymeleaf, 세션, BCrypt, H2를 유지하고 새 프레임워크나 창 저장소를 두지 않는다.

**Alternatives considered**:

- 프론트엔드 저장소를 분리한다. 같은 성공·거부를 두 경로로 판정하게 되어 001의 단일 검증 경계와 어긋난다.
- 창 전용 UI 라이브러리를 추가한다. 색, 아이콘, 글꼴 결정을 끌어와 명세의 범위 밖이다.

## Decision: 브라우저 기본 alert/confirm 대신 페이지 안 dialog를 쓴다

**Rationale**: 명세는 알림 버튼이 `확인` 하나, 확인 창 버튼이 `확인`과 `취소`라고 고정한다. 브라우저 기본 창의 버튼 문자는 운영체제 언어를 따르므로 그 문장을 보장하지 못한다. HTML `dialog`를 `showModal()`로 열면 뒤 화면 조작이 막히고, 버튼 문자를 명세와 같게 둔다. 스타일은 폭만 제한한다. 색, 로고, 글꼴 이름은 정하지 않는다.

**Alternatives considered**:

- `window.alert`와 `window.confirm`. 구현은 짧지만 버튼 문자가 환경마다 달라 FR-001을 충족하지 못한다.
- 페이지 안에 항상 보이는 문구. 진행을 막을 수 없고, 한 번에 하나의 창이라는 조건과 다르다.

## Decision: 확인은 요청 전 스크립트 게이트이고 서버 규칙은 그대로다

**Rationale**: 명확화 결과는 탈퇴, 상태 변경, 권한 변경에서 입력이 비어 있거나 나중에 거부되어도 확인 창이 먼저라는 것이다. 서버에 도달하기 전에 막아야 취소가 검증과 저장을 일으키지 않는다. 해당 폼은 `data-confirm`에 고정 질문을 두고 `novalidate`로 두어 브라우저 자체 검증 말풍선이 창보다 먼저 나오지 않게 한다. 스크립트는 첫 제출을 멈추고 확인 창을 연다. 취소는 창만 닫는다. 확인은 그 폼만 한 번 더 제출한다. 서버는 001 규칙으로 수락하거나 거부한다. 확인을 건너뛴 직접 요청도 같은 서버 규칙으로 처리한다. 확인 여부는 저장 판단의 입력이 아니다.

**Alternatives considered**:

- 서버가 확인 토큰이 없으면 거부한다. 화면 게이트를 저장 규칙으로 바꿔 001의 성공·거부 결과에 새 실패를 더한다.
- 값이 채워진 뒤에만 창을 연다. 명확화에서 기각된 선택이다.

## Decision: 성공 문장은 notice 한 필드로 한 번만 보여 준다

**Rationale**: 알림은 저장이 성공했을 때만 연다. 문장은 동작마다 고정이고 사용자 입력을 이어 붙이지 않는다. 가입, 회원정보 수정, 비밀번호 변경, 탈퇴는 기존처럼 리다이렉트하므로 플래시 `notice`로 다음 화면에 한 번 전달한다. 상태 변경과 권한 변경은 상세 화면을 그대로 다시 그리므로 그 응답의 모델 `notice`에 둔다. 템플릿은 `notice`가 있을 때만 알림 창을 그리고, 확인 버튼은 `type="button"`이라 제출하지 않는다. 실패 응답에는 `notice`를 넣지 않는다. 실패 코드는 002의 `errorForm` 위치에 그대로 둔다.

**Alternatives considered**:

- 성공 문장을 오류 코드 목록에 넣는다. 실패 코드와 성공 안내가 섞인다.
- 쿼리 문자열로 문장을 붙인다. 새로고침마다 알림이 반복되고 문장이 주소에 남는다.

## Decision: /dialogs.js는 로그인 없이 읽을 수 있다

**Rationale**: 가입 성공과 탈퇴 성공의 알림은 로그인 화면에서 열린다. 그 화면은 익명이다. 스크립트를 인증 뒤에 두면 알림 창이 열리지 않는다. 공개 경로에 `/dialogs.js`만 더한다. 001의 로그인, 회원가입, 002의 `/layout.css` 공개는 유지한다. 보호 기능의 권한 검사는 바꾸지 않는다.

**Alternatives considered**:

- 스크립트를 템플릿 안에 인라인으로 넣는다. 다섯 화면의 동작이 따로 바뀔 수 있다.
- 인증된 페이지만 스크립트를 허용한다. 로그인 화면의 가입·탈퇴 알림이 동작하지 않는다.

## Decision: 창 테스트는 003 번호를 쓰고, 001·002 테스트는 유지한다

**Rationale**: 헌법 II는 테스트가 명세 항목을 식별할 것을 요구한다. 003 테스트는 `src/test/java/com/poc/usermanagement/dialog/`에 두고 이름을 `s003Fr00N_`으로 시작한다. MockMvc로 확인 대상 폼의 질문 문장, 성공 응답의 알림 문장, 실패·로그인·로그아웃·검색에 창이 열리지 않음을 확인한다. 익명 `GET /dialogs.js`가 200인지도 확인한다. 빈 비밀번호에서 확인 창이 먼저 뜨고 취소 때 저장되지 않는 순서는 브라우저 quickstart에서 확인한다. 기존 `mvn test`는 코드와 저장 결과가 그대로인지 회귀로 다시 실행한다.

**Alternatives considered**:

- 001 테스트 이름을 003 번호로 바꾼다. 기존 추적 연결이 끊긴다.
- 브라우저 드라이버를 새로 넣어 취소 클릭까지 자동화한다. 이 PoC의 자동 테스트는 MockMvc이다. 클릭 순서는 quickstart에 남긴다.
