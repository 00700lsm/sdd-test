# Feature Specification: 알림 창과 확인 창

**Feature Branch**: `003-alert-confirm-dialogs`

**Created**: 2026-09-28

**Status**: Draft

**Input**: User description: "각종 alert confirm 창 상황에 맞게 적용"

## Clarifications

### Session 2026-09-28

- Q: 회원탈퇴나 상태·권한 변경 버튼을 눌렀을 때, 입력이 비어 있거나 나중에 거부되더라도 확인 창을 먼저 띄울까요? → A: 세 동작 모두 버튼을 누르면 확인 창이 먼저 뜬다. 확인 뒤 거부되면 성공 알림 없이 실패 코드만 보인다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 되돌리기 어려운 동작 전의 확인 (Priority: P1)

회원탈퇴, 상태 변경, 권한 변경은 실행 전에 확인 창으로 한 번 더 묻는다. 취소를 누르면 저장 결과는 바뀌지 않는다.

**Why this priority**: 탈퇴와 다른 사용자의 상태·권한 변경은 로그인 가능 여부와 권한을 바꾼다. 실수로 누르면 피해가 크다.

**Independent Test**: 각 동작에서 취소를 누르면 탈퇴 상태, 탈퇴 시점, 상태, 권한이 누르기 전과 같다. 확인을 누르면 기존 사용자 관리 규칙대로 진행된다.

**Acceptance Scenarios**:

1. **Given** 로그인한 사용자와 탈퇴해도 ACTIVE 관리자가 한 명 이상 남는 계정, **When** 탈퇴를 요청하면, **Then** 저장 전에 확인 창이 뜨고 문장은 "탈퇴하면 이 계정으로 다시 로그인할 수 없습니다. 탈퇴할까요?"이다. (FR-001, FR-002)
2. **Given** 그 확인 창, **When** 취소를 누르면, **Then** 창만 닫히고 상태는 그대로이며 탈퇴 시점은 기록되지 않고 로그인 상태도 유지된다. 실패 코드는 생기지 않는다. (FR-002, FR-008)
3. **Given** 그 확인 창과 올바른 현재 비밀번호, **When** 확인을 누르면, **Then** 기존 탈퇴 규칙대로 WITHDRAWN이 되고 탈퇴 시점이 기록되며 로그인 상태가 끝난다. (FR-002, FR-010)
4. **Given** 관리자와 상태 변경이 허용되는 사용자, **When** 상태 변경을 요청하면, **Then** 저장 전에 "이 사용자의 상태를 변경할까요?" 확인 창이 뜬다. 취소하면 상태는 그대로이다. (FR-001, FR-003)
5. **Given** 관리자와 권한 변경이 허용되는 사용자, **When** 권한 변경을 요청하면, **Then** 저장 전에 "이 사용자의 권한을 변경할까요?" 확인 창이 뜬다. 취소하면 권한은 그대로이다. (FR-001, FR-004)
6. **Given** 탈퇴 비밀번호가 비어 있거나 틀림, **When** 탈퇴를 요청하면, **Then** 확인 창이 먼저 뜬다. 확인을 누르면 기존 규칙으로 거부되고 성공 알림은 없으며 실패 코드는 탈퇴 묶음 위에만 보인다. 취소를 누르면 검증하지 않고 실패 코드도 없으며 입력은 그대로이다. (FR-002, FR-008, FR-011)

### User Story 2 - 저장 성공 후의 알림 (Priority: P2)

가입, 회원정보 수정, 비밀번호 변경, 탈퇴, 상태 변경, 권한 변경이 실제로 성공했을 때만 알림 창으로 결과를 알려 준다.

**Why this priority**: 성공했는지 화면만으로는 지나치기 쉽다. 다만 확인 창으로 실수부터 막은 뒤에 두는 안내이다.

**Independent Test**: 각 성공 한 건마다 지정한 문장의 알림이 한 번 보이고, 그 문장에 비밀번호가 없다. 알림의 확인을 눌러도 같은 저장이 반복되지 않는다.

**Acceptance Scenarios**:

1. **Given** 규칙을 만족하는 새 가입 정보, **When** 가입이 성공하면, **Then** "가입되었습니다." 알림이 한 번 보인다. 방문자 본인은 로그인되지 않는다. (FR-005, FR-006)
2. **Given** 로그인한 사용자와 사용 중이 아닌 이메일, **When** 이름·이메일 수정이 성공하면, **Then** "회원정보를 수정했습니다." 알림이 한 번 보이고 이후 본인 조회에 바뀐 값이 있다. (FR-005, FR-006)
3. **Given** 로그인한 사용자와 규칙을 만족하는 새 비밀번호, **When** 비밀번호 변경이 성공하면, **Then** "비밀번호를 변경했습니다." 알림이 한 번 보이고 로그인 상태는 유지된다. 알림 문장에 비밀번호 원문은 없다. (FR-005, FR-009)
4. **Given** 탈퇴 확인을 눌러 탈퇴가 성공함, **When** 결과가 알려지면, **Then** "탈퇴했습니다." 알림이 한 번 보인다. 알림을 닫으면 로그인 상태가 끝난 뒤의 결과와 같다. (FR-005, FR-006, FR-010)
5. **Given** 상태 변경 확인을 눌러 변경이 성공함, **When** 결과가 알려지면, **Then** "상태를 변경했습니다." 알림이 한 번 보인다. 대상 사용자의 다른 화면에는 이 알림을 띄우지 않는다. (FR-005, FR-007)
6. **Given** 권한 변경 확인을 눌러 변경이 성공함, **When** 결과가 알려지면, **Then** "권한을 변경했습니다." 알림이 한 번 보인다. 권한 변경만으로 대상의 로그인 상태가 끝나지는 않는다. (FR-005, FR-010)

### User Story 3 - 창을 띄우지 않는 상황 (Priority: P3)

로그인, 로그아웃, 검색, 화면 이동과 가입·회원정보 수정·비밀번호 변경의 입력 실패는 알림 창이나 확인 창을 띄우지 않는다. 탈퇴·상태 변경·권한 변경은 입력이 비어 있거나 나중에 거부되어도 확인 창이 먼저 뜨고, 확인 뒤 거부되면 성공 알림 없이 실패 코드만 해당 묶음 위에 보인다.

**Why this priority**: 모든 버튼에 창을 띄우면 기존 실패 표시와 겹치고, 검색·이동까지 막는다. 경계를 고정해야 앞의 두 이야기가 과하게 퍼지지 않는다.

**Independent Test**: 로그인 실패, 가입·수정·비밀번호 변경의 형식 오류, 로그아웃, 검색, 링크 이동에서 알림 창과 확인 창이 없다. 실패 코드는 해당 묶음 위에 남는다.

**Acceptance Scenarios**:

1. **Given** 로그인 화면과 틀린 비밀번호, **When** 로그인을 요청하면, **Then** 알림 창과 확인 창이 없고 기존 로그인 실패 표시만 보인다. 로그인 상태는 생기지 않는다. (FR-007, FR-011)
2. **Given** 가입·이름과 이메일 수정·비밀번호 변경 입력 중 규칙 위반, **When** 해당 동작을 요청하면, **Then** 알림 창과 확인 창이 없다. 실패 코드는 그 묶음의 입력칸 바로 위에만 있고 창 안에 같은 코드를 반복하지 않는다. (FR-007, FR-011)
3. **Given** 로그인한 사용자, **When** 로그아웃하거나 검색하거나 화면 링크를 누르면, **Then** 알림 창과 확인 창이 없다. (FR-007)
4. **Given** 마지막 ACTIVE 관리자의 탈퇴 또는 권한·상태 변경, **When** 확인 창에서 확인을 눌러도 규칙상 거부되면, **Then** 성공 알림이 없고 계정은 ACTIVE 관리자로 남으며 실패 코드는 해당 묶음 위에만 보인다. (FR-008, FR-010, FR-011)

### Edge Cases

- 탈퇴, 상태 변경, 권한 변경은 입력이 비어 있거나 나중에 거부되어도 버튼을 누르는 즉시 확인 창이 먼저 열린다. 취소하면 검증과 저장을 하지 않는다. 확인한 뒤에만 기존 검증과 업무 규칙을 적용한다.
- 확인 창의 취소는 입력칸을 비우거나 실패 코드를 만들지 않는다. 비밀번호 원문은 창 문장에 나타나지 않고, 칸 안에서는 기존처럼 가려진다.
- 확인을 누른 뒤 비밀번호 불일치, 중복, 권한 없음, 탈퇴 계정 변경처럼 기존 규칙으로 거부되면 성공 알림은 없다. 비밀번호 칸은 기존 화면 규칙대로 비운다.
- 성공 알림과 확인 창은 한 단계에 함께 떠 있지 않는다. 확인 창을 닫기 전에는 성공 알림이 없다.
- 알림의 확인은 창만 닫는다. 가입, 수정, 비밀번호 변경, 탈퇴, 상태 변경, 권한 변경을 한 번 더 실행하지 않는다.
- 창이 열려 있는 동안 뒤 화면의 다른 버튼으로 다음 동작을 진행할 수 없다.
- 상태 변경 알림은 변경을 실행한 관리자에게만 보인다. 대상 사용자가 비활성화되며 끊기는 로그인에는 별도의 알림 창을 띄우지 않는다.
- 이미 로그인한 사용자의 추가 가입·추가 로그인은 기존처럼 거부되고 성공 알림이 없다.
- 가로 390px 창에서도 열려 있는 창의 확인 또는 취소에 페이지 전체를 가로로 밀지 않고 도달한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 사용자에게 보이는 창은 두 종류뿐이다. 알림 창은 결과 문장과 확인 버튼 하나만 가진다. 확인 창은 질문 문장과 확인 버튼, 취소 버튼을 가진다. 다른 버튼은 두지 않는다.
- **FR-002**: 회원탈퇴를 요청하면, 입력이 비어 있거나 나중에 거부되더라도 검증과 저장 전에 확인 창을 연다. 문장은 "탈퇴하면 이 계정으로 다시 로그인할 수 없습니다. 탈퇴할까요?"이다. 취소하면 검증하지 않고 상태, 탈퇴 시점, 로그인 상태가 바뀌지 않는다. 확인하면 기존 탈퇴 규칙을 적용한다.
- **FR-003**: 상태 변경을 요청하면, 나중에 거부되더라도 검증과 저장 전에 확인 창을 연다. 문장은 "이 사용자의 상태를 변경할까요?"이다. 취소하면 검증하지 않고 상태는 바뀌지 않는다. 확인하면 기존 상태 변경 규칙을 적용한다.
- **FR-004**: 권한 변경을 요청하면, 나중에 거부되더라도 검증과 저장 전에 확인 창을 연다. 문장은 "이 사용자의 권한을 변경할까요?"이다. 취소하면 검증하지 않고 권한은 바뀌지 않는다. 확인하면 기존 권한 변경 규칙을 적용한다.
- **FR-005**: 다음 동작이 실제로 성공했을 때만 알림 창을 한 번 연다. 문장은 동작마다 하나로 고정한다. 가입은 "가입되었습니다.", 이름·이메일 수정은 "회원정보를 수정했습니다.", 비밀번호 변경은 "비밀번호를 변경했습니다.", 탈퇴는 "탈퇴했습니다.", 상태 변경은 "상태를 변경했습니다.", 권한 변경은 "권한을 변경했습니다."
- **FR-006**: 알림 창의 확인은 그 창만 닫는다. 같은 저장을 다시 실행하지 않는다. 닫은 뒤의 로그인 상태와 저장 결과는 기존 사용자 관리의 성공 결과와 같다.
- **FR-007**: 로그인 성공, 로그인 실패, 로그아웃, 검색, 페이지 이동, 화면 링크 이동에는 알림 창과 확인 창을 열지 않는다. 이 기능이 해당 동작의 기존 결과를 바꾸지 않는다.
- **FR-008**: 확인 창에서 취소하면 실패 코드를 만들지 않고 입력값을 지우지 않는다. 확인을 누른 뒤 기존 규칙으로 거부되면 성공 알림을 열지 않는다.
- **FR-009**: 알림 창과 확인 창의 문장에 비밀번호 원문을 넣지 않는다. 창은 한 번에 하나만 연다. 열린 동안에는 뒤 화면의 다른 동작을 진행할 수 없다.
- **FR-010**: 확인을 눌러 진행한 뒤의 검증, 역할 검사, 상태 전이, 탈퇴의 논리 삭제, 저장 결과는 기존 사용자 관리와 같다. 이 기능이 바꾸는 것은 진행 전 확인과 성공 후 알림뿐이다.
- **FR-011**: 입력 검증 실패와 업무 규칙 거부의 실패 코드는 기존 화면 표시 규칙대로 그 동작 묶음의 입력칸 바로 위에만 보인다. 같은 코드를 알림 창이나 확인 창에 반복하지 않는다.

### Key Entities

- **알림 창**: 이미 성공한 결과만 알려 주는 창. 문장 하나와 확인 버튼 하나를 가진다. 저장 값을 다시 바꾸지 않는다.
- **확인 창**: 탈퇴, 상태 변경, 권한 변경을 저장하기 전에 진행 여부를 묻는 창. 확인은 기존 규칙을 진행하고, 취소는 저장 결과를 그대로 둔다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 회원탈퇴, 상태 변경, 권한 변경에서 취소를 누르면, 상태·탈퇴 시점·권한이 요청 전과 100% 같다.
- **SC-002**: 가입, 회원정보 수정, 비밀번호 변경, 탈퇴, 상태 변경, 권한 변경의 성공 각 1회마다 지정 문장 알림이 정확히 한 번 보이고, 여섯 문장 어디에도 비밀번호가 없다.
- **SC-003**: 로그인 실패, 입력 검증 실패, 로그아웃, 검색, 화면 이동 각 1회에서 알림 창과 확인 창이 0번 나타난다.
- **SC-004**: 확인을 누른 뒤의 성공·거부 결과와 오류 코드는 기존 사용자 관리와 100% 같다.
- **SC-005**: 알림의 확인 1회가 같은 저장을 추가로 실행하는 횟수는 0이다. 창이 열린 동안 뒤 화면의 다른 동작이 진행되는 횟수도 0이다.

## Assumptions

- 확인이 필요한 상황은 회원탈퇴, 상태 변경, 권한 변경뿐이다. 이 세 동작은 입력이 비어 있거나 나중에 거부되어도 확인 창이 먼저다. 이름·이메일 수정과 비밀번호 변경은 본인 확인 입력이 이미 있거나 쉽게 다시 고칠 수 있으므로 확인 창 없이 성공 알림만 둔다.
- 로그아웃, 검색, 페이지 이동, 화면 링크는 저장을 바꾸지 않거나 바로 되돌릴 수 있으므로 창을 띄우지 않는다.
- 로그인 성공은 다음 화면으로 충분하므로 알림을 띄우지 않는다. 로그인 실패와 그 밖의 거부는 기존 실패 코드 표시를 유지하고 창으로 대체하지 않는다.
- 창의 색, 아이콘, 위치, 글꼴 이름은 정하지 않는다. 문장과 버튼이 읽히고, 좁은 창에서 확인 또는 취소에 도달하면 된다.
- 문구는 한국어이며 위 문장 그대로이다. 실패 코드를 다른 문장으로 바꾸지 않는다.
- 대상 사용자가 다른 화면을 보고 있는 동안에는 관리자 동작의 알림을 대신 보여 주지 않는다. 그 사용자의 로그인 종료 시점은 기존 사용자 관리를 따른다.
