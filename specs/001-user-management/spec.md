# Feature Specification: 사용자 관리

**Feature Branch**: `001-user-management`

**Created**: 2026-09-28

**Status**: Draft

**Input**: User description: "사용자 관리 프로그램을 개발한다. 일반 사용자는 회원가입, 로그인, 로그아웃, 자신의 회원정보 조회, 자신의 회원정보 수정, 비밀번호 변경, 회원탈퇴를 사용할 수 있다. 관리자는 사용자 목록 조회, 사용자 검색, 사용자 상세 조회, 사용자 상태 변경, 사용자 권한 변경을 사용할 수 있다. 회원가입 시 아이디, 비밀번호, 이름, 이메일을 입력한다. 아이디와 이메일은 중복될 수 없다. 일반 사용자는 다른 사용자의 개인정보를 조회하거나 수정할 수 없다. 회원탈퇴는 Soft Delete로 처리하며, 탈퇴한 사용자는 로그인할 수 없다. 사용자 권한은 최소 USER와 ADMIN으로 구분한다. 사용자 상태는 최소 ACTIVE, INACTIVE, WITHDRAWN으로 구분한다. 이번 PoC에서는 화면 디자인보다 사용자 관리 CRUD, 권한 관리, 요구사항과 구현 및 테스트 간 추적성을 검증하는 데 집중한다."

## Clarifications

### Session 2026-09-28

- Q: 관리자가 이미 로그인한 사용자를 비활성화하거나 권한을 바꾸면, 그 사용자의 현재 로그인에는 언제 반영되나요? → A: 다음 요청부터 즉시 반영한다. INACTIVE가 되면 그 사용자의 진행 중인 로그인 상태가 끝나고, 권한 변경은 이미 로그인된 상태의 다음 보호 기능부터 새 권한을 따른다.
- Q: 관리자 기능을 검증할 첫 ACTIVE ADMIN 계정은 어떻게 준비되나요? → A: 사용 시작 시 검증용 ACTIVE ADMIN 한 명(아이디 `admin`)이 이미 있다. 공개 회원가입으로는 만들 수 없고, 비밀번호 원문은 명세에 적지 않는다.
- Q: 관리자는 사용자 검색에서 아이디, 이름, 이메일을 어떻게 입력하나요? → A: 검색어 하나를 아이디, 이름, 이메일에 각각 일부 일치로 비교하고, 하나라도 맞으면 결과에 포함한다.
- Q: 회원가입이나 회원정보 수정에서 여러 항목이 동시에 규칙에 어긋나면, 실패 결과를 어떻게 돌려주나요? → A: 실패한 모든 항목과 각 실패 이유를 한 결과에 함께 알려 준다.
- Q: 관리자의 사용자 목록과 검색 결과는 한 번에 얼마나 보여 주나요? → A: 한 페이지에 20명씩 보여 주고, 다음 페이지로 이어서 볼 수 있다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 회원가입과 로그인 (Priority: P1)

방문자는 아이디, 비밀번호, 이름, 이메일을 입력해 계정을 만들고, 그 아이디와 비밀번호로 로그인한다. 새 계정의 권한은 USER이고 상태는 ACTIVE이다.

**Why this priority**: 이후의 본인 기능과 관리 기능은 로그인할 수 있는 계정이 있어야 검증할 수 있다.

**Independent Test**: 새 아이디와 이메일로 가입한 뒤 그 자격으로 로그인하면, 자신의 이름과 이메일을 가진 USER/ACTIVE 계정으로 들어간다.

**Acceptance Scenarios**:

1. **Given** 사용 중이 아닌 아이디와 이메일, **When** 방문자가 규칙을 만족하는 아이디, 비밀번호, 이름, 이메일로 가입하면, **Then** USER 권한과 ACTIVE 상태의 계정이 만들어지고 비밀번호 원문은 어디에도 표시되지 않는다. (FR-001, FR-005, FR-006)
2. **Given** ACTIVE 계정, **When** 올바른 아이디와 비밀번호로 로그인하면, **Then** 그 사용자로 로그인한 상태가 된다. (FR-007)
3. **Given** 이미 있는 아이디 또는 이메일, **When** 방문자가 그 값으로 가입하면, **Then** 계정은 만들어지지 않고 아이디 중복인지 이메일 중복인지 구분되는 실패 결과를 받는다. 둘 다 중복이면 두 이유가 한 결과에 함께 담긴다. (FR-002, FR-003, FR-004)
4. **Given** 필수 값이 빠졌거나 형식·길이가 규칙에 맞지 않는 입력, **When** 방문자가 가입하면, **Then** 계정은 만들어지지 않고, 실패한 모든 항목과 각 실패 이유가 한 결과에 함께 담긴다. (FR-002)

---

### User Story 2 - 로그아웃 (Priority: P2)

로그인한 사용자는 로그아웃해 로그인 상태를 끝낸다.

**Why this priority**: 공용 환경에서 로그인 상태를 직접 종료할 수 있어야 이후 보호 기능이 다시 로그인을 요구하는지 검증할 수 있다.

**Independent Test**: ACTIVE 계정으로 로그인한 뒤 로그아웃하면, 회원정보 조회는 다시 로그인을 요구한다.

**Acceptance Scenarios**:

1. **Given** 로그인한 사용자, **When** 로그아웃하면, **Then** 로그인 상태가 끝나고 회원정보 조회, 수정, 비밀번호 변경, 탈퇴, 관리자 기능은 다시 로그인을 요구한다. (FR-009, FR-017)
2. **Given** 로그인하지 않은 방문자, **When** 로그아웃을 요청하면, **Then** 로그인 상태는 생기지 않고 요청은 거부된다. (FR-009)

---

### User Story 3 - 내 회원정보 조회와 수정 (Priority: P2)

로그인한 사용자는 자신의 회원정보를 보고, 이름과 이메일을 고친다. 다른 사용자의 정보는 보거나 고칠 수 없다.

**Why this priority**: 개인정보 격리는 이 PoC의 핵심 권한 규칙이며, 본인 조회·수정이 그 기준선이다.

**Independent Test**: USER로 로그인해 자신의 이름과 이메일을 수정한 뒤 다시 조회하면 변경 값이 보이고, 다른 사용자 식별자로 조회하거나 수정하면 대상 정보가 반환되지 않는다.

**Acceptance Scenarios**:

1. **Given** 로그인한 사용자, **When** 자신의 회원정보를 조회하면, **Then** 아이디, 이름, 이메일, 권한, 상태가 보이고 비밀번호 원문은 보이지 않는다. (FR-010)
2. **Given** 로그인한 사용자와 사용 중이 아닌 새 이메일, **When** 자신의 이름과 이메일을 수정하면, **Then** 이후 본인 조회에 변경된 이름과 이메일이 보인다. 아이디, 권한, 상태는 그대로이다. (FR-011)
3. **Given** 로그인한 USER와 다른 사용자, **When** USER가 그 사용자의 식별자로 정보를 조회하거나 수정하면, **Then** 요청은 거부되고 상대의 개인정보는 반환되지 않는다. (FR-015)
4. **Given** 로그인한 사용자와 다른 계정이 이미 쓰는 이메일, **When** 자신의 이메일을 그 값으로 바꾸면, **Then** 수정은 거부되고 기존 이메일이 유지된다. (FR-004, FR-011)
5. **Given** 로그인한 ADMIN, **When** 자신의 회원정보를 조회하고 이름과 이메일을 수정하면, **Then** 본인 정보가 변경되어 보이고 아이디, 권한, 상태는 그대로이다. (FR-010, FR-011, FR-025)

### User Story 4 - 비밀번호 변경 (Priority: P2)

로그인한 사용자는 현재 비밀번호를 확인한 뒤 새 비밀번호로 바꾼다.

**Why this priority**: 비밀번호는 본인만 바꿀 수 있어야 하며, 변경 후에는 이전 비밀번호로 들어갈 수 없어야 한다.

**Independent Test**: 현재 비밀번호로 새 비밀번호를 설정한 뒤 로그아웃하고, 이전 비밀번호 로그인은 실패하고 새 비밀번호 로그인은 성공한다.

**Acceptance Scenarios**:

1. **Given** 로그인한 USER 또는 ADMIN, **When** 현재 비밀번호와 규칙을 만족하는 다른 새 비밀번호로 변경하면, **Then** 이전 비밀번호로는 로그인할 수 없고 새 비밀번호로는 로그인할 수 있다. 원문은 표시되지 않는다. (FR-006, FR-012, FR-025)
2. **Given** 로그인한 사용자, **When** 현재 비밀번호가 틀리거나 새 비밀번호가 규칙을 만족하지 않으면, **Then** 비밀번호는 바뀌지 않는다. 두 실패가 함께 있으면 두 이유가 한 결과에 담긴다. (FR-002, FR-012)
3. **Given** 로그인한 USER와 다른 사용자, **When** USER가 그 사용자의 비밀번호 변경을 시도하면, **Then** 요청은 거부되고 상대 비밀번호는 바뀌지 않는다. (FR-015)

---

### User Story 5 - 회원탈퇴 (Priority: P2)

로그인한 사용자는 현재 비밀번호를 확인하고 탈퇴한다. 계정 기록은 남고 상태는 WITHDRAWN이 되며, 그 계정으로는 다시 로그인할 수 없다.

**Why this priority**: Soft Delete와 탈퇴 후 로그인 금지는 헌법의 데이터 보존 규칙과 직결된다.

**Independent Test**: 비밀번호를 확인하고 탈퇴한 뒤 같은 아이디와 비밀번호로 로그인하면 실패하고, 관리자가 탈퇴 사용자를 포함해 조회하면 기록과 탈퇴 시점이 남아 있다.

**Acceptance Scenarios**:

1. **Given** 로그인한 USER 또는 ADMIN이고 이 탈퇴로 ACTIVE ADMIN이 0명이 되지 않음, **When** 현재 비밀번호를 확인하고 탈퇴하면, **Then** 로그인 상태가 끝나고 상태는 WITHDRAWN이며 탈퇴 시점이 기록된다. 계정 기록은 삭제되지 않는다. (FR-013, FR-024, FR-025)
2. **Given** WITHDRAWN 계정, **When** 올바른 아이디와 비밀번호로 로그인하면, **Then** 로그인 상태로 들어가지 않는다. (FR-008, FR-014)
3. **Given** 로그인한 사용자, **When** 현재 비밀번호가 틀린 채로 탈퇴하면, **Then** 상태는 그대로이고 탈퇴 시점은 기록되지 않는다. (FR-013)
4. **Given** 유일한 ACTIVE ADMIN, **When** 그 계정이 탈퇴를 시도하면, **Then** 탈퇴는 거부되고 계정은 ACTIVE ADMIN으로 남는다. (FR-023)

### User Story 6 - 관리자의 사용자 조회와 검색 (Priority: P3)

ADMIN은 사용자 목록을 보고, 아이디·이름·이메일로 검색하며, 한 사용자의 상세를 본다. 기본 결과에는 탈퇴 사용자가 빠지고, 이력 확인이 필요할 때만 탈퇴 사용자를 포함한다.

**Why this priority**: 관리 조회의 범위와 탈퇴 사용자 제외 규칙이 정해져야 상태·권한 변경의 대상을 고를 수 있다.

**Independent Test**: ACTIVE와 INACTIVE, WITHDRAWN 사용자가 있는 상태에서 ADMIN 기본 목록에는 탈퇴 사용자가 없고, 탈퇴 포함 조회와 아이디 지정 상세에서는 탈퇴 시점까지 보인다. USER의 동일 시도는 거부된다.

**Acceptance Scenarios**:

1. **Given** ADMIN과 ACTIVE, INACTIVE, WITHDRAWN 사용자, **When** ADMIN이 기본 목록을 조회하면, **Then** ACTIVE와 INACTIVE만 아이디, 이름, 이메일, 권한, 상태로 보이고 비밀번호는 없으며 WITHDRAWN은 빠진다. (FR-018)
2. **Given** ADMIN과 아이디, 이름, 이메일 중 한 곳에만 검색어가 포함된 사용자, **When** ADMIN이 그 검색어 하나로 검색하면, **Then** 그 사용자가 결과에 포함된다. 세 항목 중 어디에도 일부 일치하지 않으면 빈 결과가 반환된다. 비교는 대소문자를 구분하지 않는다. (FR-019)
3. **Given** ADMIN과 WITHDRAWN 사용자, **When** ADMIN이 탈퇴 사용자 포함을 선택해 목록 또는 검색을 하거나 그 아이디의 상세를 보면, **Then** 상세와 포함 결과에 탈퇴 시점, 권한, 상태가 보이고 비밀번호는 없다. (FR-018, FR-019, FR-020)
4. **Given** 로그인한 USER, **When** 목록, 검색, 다른 사용자 상세를 요청하면, **Then** 요청은 거부되고 다른 사용자의 개인정보는 반환되지 않는다. (FR-016)
5. **Given** 사용 시작 상태, **When** 아이디 `admin`과 준비된 비밀번호로 로그인하면, **Then** ADMIN/ACTIVE로 사용자 목록을 조회할 수 있다. 공개 회원가입으로 아이디 `admin`을 만들 수는 없다. (FR-003, FR-007, FR-018, FR-026)
6. **Given** 기본 목록 대상이 21명, **When** ADMIN이 목록의 첫 페이지를 보면, **Then** 최근 가입 20명이 보인다. 다음 페이지에는 나머지 1명이 보이고, 그 페이지에서 이전 페이지로 돌아오면 처음 20명이 다시 보인다. (FR-018)

### User Story 7 - 관리자의 상태와 권한 변경 (Priority: P3)

ADMIN은 사용자의 상태를 ACTIVE와 INACTIVE 사이에서 바꾸고, 권한을 USER와 ADMIN 사이에서 바꾼다. 탈퇴 처리와 탈퇴 계정의 상태·권한 변경은 하지 않는다.

**Why this priority**: 권한 분리와 상태 전이는 조회가 가능한 뒤에야 대상 사용자를 골라 검증할 수 있다.

**Independent Test**: ADMIN이 ACTIVE USER를 INACTIVE로 바꾸면 그 사용자는 로그인할 수 없고, 다시 ACTIVE로 바꾸면 로그인할 수 있다. 같은 ADMIN이 그 사용자 권한을 ADMIN으로 바꾸면 관리자 목록 조회가 가능하다.

**Acceptance Scenarios**:

1. **Given** ADMIN과 ACTIVE 사용자, **When** ADMIN이 그 사용자를 INACTIVE로 바꾸면, **Then** 상태는 INACTIVE가 되고 그 사용자는 로그인할 수 없다. 변경 전에 진행 중인 로그인이 있으면 그 로그인 상태는 즉시 끝나고, 이후 보호 기능은 다시 로그인을 요구한다. 다시 ACTIVE로 바꾸면 로그인할 수 있다. (FR-008, FR-017, FR-021)
2. **Given** ADMIN과 ACTIVE 또는 INACTIVE 사용자, **When** ADMIN이 권한을 USER 또는 ADMIN으로 바꾸면, **Then** 이미 로그인된 상태를 포함해 다음 보호 기능부터 새 권한을 따른다. 권한 변경만으로 로그인 상태가 끝나지는 않는다. (FR-022)
3. **Given** ADMIN과 WITHDRAWN 사용자, **When** ADMIN이 상태를 바꾸거나 권한을 바꾸면, **Then** 변경은 거부되고 WITHDRAWN과 기존 권한이 유지된다. (FR-021, FR-022)
4. **Given** 로그인한 USER, **When** 다른 사용자의 상태나 권한을 바꾸면, **Then** 요청은 거부되고 대상의 상태와 권한은 유지된다. (FR-016)
5. **Given** 유일한 ACTIVE ADMIN, **When** 그 계정의 권한을 USER로 바꾸거나 상태를 INACTIVE로 바꾸면, **Then** 변경은 거부되고 ACTIVE ADMIN으로 남는다. (FR-023)

---

### Edge Cases

- 아이디와 이메일의 앞뒤 공백은 제거한 뒤 형식과 중복을 검사한다. 이름도 앞뒤 공백을 제거한 뒤 길이를 검사하며, 공백만 있는 이름은 거부한다.
- 아이디 `User`와 `user`는 같은 아이디로 본다. 이메일 `A@Example.com`과 `a@example.com`은 같은 이메일로 본다. 나중 가입은 거부된다.
- 탈퇴해 WITHDRAWN으로 남은 아이디와 이메일도 중복으로 본다. 같은 값으로는 다시 가입할 수 없다.
- 아이디 길이가 4자, 20자이면 다른 규칙을 만족할 때 가입할 수 있다. 3자, 21자, 영문 소문자로 시작하지 않는 값, 허용되지 않은 문자는 거부된다.
- 회원가입에서 아이디가 규칙을 어기고 이메일이 중복이면 계정은 만들어지지 않고, 두 실패 이유가 한 결과에 함께 담긴다. 이름 수정에서 길이를 넘고 이메일이 중복이면 기존 값은 유지되고 두 이유가 한 결과에 함께 담긴다. (FR-002, FR-004, FR-011)
- 비밀번호 길이가 8자, 64자이면 아이디와 다르지 않은 한 사용할 수 있다. 7자, 65자, 아이디와 같은 비밀번호는 거부된다.
- 사용자는 자신의 현재 이메일로 이메일을 다시 저장할 수 있다. 그 경우는 중복으로 보지 않는다.
- 로그인 실패는 아이디가 없을 때, 비밀번호가 틀릴 때, 상태가 INACTIVE일 때, 상태가 WITHDRAWN일 때 모두 로그인 상태를 만들지 않는다. 실패 결과는 계정 존재 여부와 상태를 구분하지 않는다.
- 검색어가 비어 있으면 기본 목록과 같은 결과를 반환한다. 일치하는 사용자가 없으면 오류가 아니라 빈 결과를 반환한다.
- 목록과 검색은 한 페이지에 최대 20명이다. 대상이 20명이면 다음 페이지는 없고, 21명이면 첫 페이지 20명과 다음 페이지 1명이다. 다음 페이지에서 이전 페이지로 돌아올 수 있다. 다음 페이지가 없을 때 다음으로 이동하면 현재 페이지의 사용자가 유지된다. (FR-018, FR-019)
- 검색어 하나가 어떤 사용자의 이름과 다른 사용자의 아이디 또는 이메일에 각각 일부 일치하면 두 사용자 모두 반환된다. 세 항목이 모두 일치해야 반환되지는 않는다. (FR-019)
- 같은 아이디 또는 같은 이메일로 가입 요청이 겹치면 하나의 계정만 만들어진다.
- 아이디 `admin` 또는 그와 대소문자만 다른 값으로 회원가입하면 아이디 중복으로 거부된다. (FR-003, FR-026)
- 상태 변경으로 WITHDRAWN을 지정하는 요청은 거부된다. 탈퇴는 본인의 탈퇴 기능으로만 WITHDRAWN이 된다.
- 관리자가 사용자를 INACTIVE로 바꾸면 그 사용자의 진행 중인 모든 로그인 상태가 끝난다. 권한을 바꾸면 로그인 상태는 유지되고 다음 보호 기능부터 새 권한이 적용된다. 자동 만료 시간은 두지 않는다. (FR-021, FR-022)
- ADMIN은 자신의 이름, 이메일, 비밀번호를 본인 기능으로 바꿀 수 있다. 자신의 상태와 권한은 관리자 기능으로만 바꾸며, 마지막 ACTIVE ADMIN 보호 규칙을 따른다.
- 이미 로그인한 사용자가 회원가입이나 다른 로그인을 다시 시도하면 새 계정과 새 로그인 상태는 만들어지지 않고, 현재 로그인 상태가 유지된 채 요청은 거부된다. (FR-001, FR-007)
- 화면의 색, 배치, 간격을 맞추지 못한 경우에도 각 시나리오의 결과 데이터가 맞으면 해당 기능은 성공으로 본다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 방문자는 아이디, 비밀번호, 이름, 이메일을 입력해 회원가입할 수 있어야 한다. 이미 로그인한 사용자의 추가 회원가입은 거부하고 현재 로그인 상태를 유지해야 한다.
- **FR-002**: 시스템은 처리 전에 모든 사용자 입력을 검사해야 한다. 화면 단계의 검사만으로는 충족하지 않는다. 실패하면 어떤 변경도 저장하지 않고, 실패한 모든 항목과 각 실패 이유를 한 결과에 함께 반환해야 한다. 규칙은 다음과 같다.
  - 아이디: 필수. 앞뒤 공백 제거 후 4자 이상 20자 이하. 영문 소문자, 숫자, 밑줄만 허용하고 첫 글자는 영문 소문자. 입력에 포함된 영문 대문자는 소문자로 맞춘 뒤 검사하고 그 값을 아이디로 사용한다.
  - 비밀번호: 필수. 8자 이상 64자 이하. 아이디와 같으면 거부한다.
  - 이름: 필수. 앞뒤 공백 제거 후 1자 이상 50자 이하.
  - 이메일: 필수. 앞뒤 공백 제거 후 254자 이하이고, 로컬부와 도메인이 `@`로 구분된 이메일 형식이어야 한다.
- **FR-003**: 아이디는 모든 상태에서 중복될 수 없다. 대소문자는 구분하지 않는다. 중복이면 계정을 만들지 않고 아이디 중복임을 알려야 한다.
- **FR-004**: 이메일은 모든 상태에서 중복될 수 없다. 대소문자는 구분하지 않는다. 중복이면 가입 또는 수정을 거부하고 이메일 중복임을 알려야 한다. 본인이 현재 이메일을 다시 저장하는 경우는 중복이 아니다.
- **FR-005**: 회원가입으로 만든 계정의 권한은 USER이고 상태는 ACTIVE이어야 한다.
- **FR-006**: 비밀번호 원문은 보관 내용에서 되돌릴 수 없어야 한다. 조회 결과, 실패 메시지, 기록에 비밀번호 원문을 포함하지 않아야 한다.
- **FR-007**: 로그인하지 않은 방문자는 ACTIVE 사용자의 아이디와 비밀번호로 로그인할 수 있어야 한다. 이미 로그인한 상태에서 다시 로그인하는 요청은 거부하고 현재 로그인 상태를 유지해야 한다.
- **FR-008**: 로그인에 실패하면 로그인 상태로 들어가지 않아야 한다. 아이디가 없음, 비밀번호 불일치, INACTIVE, WITHDRAWN은 서로 구분되지 않는 같은 실패 결과를 반환해야 한다.
- **FR-009**: 로그인한 사용자는 로그아웃할 수 있어야 한다. 로그아웃 후 보호 기능은 다시 로그인을 요구해야 한다. 로그인하지 않은 방문자의 로그아웃은 거부해야 한다.
- **FR-010**: 로그인한 사용자는 자신의 아이디, 이름, 이메일, 권한, 상태를 조회할 수 있어야 한다. 결과에는 비밀번호 원문이 없어야 한다.
- **FR-011**: 로그인한 사용자는 자신의 이름과 이메일만 수정할 수 있어야 한다. 아이디, 권한, 상태는 이 기능으로 바뀌지 않아야 한다.
- **FR-012**: 로그인한 사용자는 현재 비밀번호가 일치할 때만 비밀번호를 바꿀 수 있어야 한다. 새 비밀번호는 FR-002의 비밀번호 규칙을 만족하고 현재 비밀번호와 달라야 한다. 변경 후 이전 비밀번호로는 로그인할 수 없어야 한다.
- **FR-013**: 로그인한 사용자는 현재 비밀번호가 일치할 때만 탈퇴할 수 있어야 한다. 탈퇴는 기록을 지우지 않고 상태를 WITHDRAWN으로 바꾸며 탈퇴 시점을 남겨야 한다. 진행 중인 로그인 상태는 끝나야 한다.
- **FR-014**: WITHDRAWN 사용자는 로그인할 수 없어야 한다.
- **FR-015**: USER는 다른 사용자의 개인정보를 조회하거나 수정할 수 없어야 한다. 식별자를 바꿔 요청해도 거부하고 대상 정보를 반환하지 않아야 한다. 다른 사용자의 이름, 이메일, 비밀번호도 바꾸지 않아야 한다.
- **FR-016**: USER는 사용자 목록 조회, 사용자 검색, 다른 사용자 상세 조회, 사용자 상태 변경, 사용자 권한 변경을 할 수 없어야 한다. 거부 시 다른 사용자의 개인정보를 반환하지 않아야 한다.
- **FR-017**: 로그인하지 않은 방문자는 회원정보 조회, 회원정보 수정, 비밀번호 변경, 회원탈퇴, 관리자 기능을 사용할 수 없어야 한다.
- **FR-018**: ADMIN은 사용자 목록을 조회할 수 있어야 한다. 기본 목록은 ACTIVE와 INACTIVE만 포함하며, 최근 가입 순으로 아이디, 이름, 이메일, 권한, 상태를 보여 준다. 비밀번호는 포함하지 않는다. 한 페이지에는 최대 20명이며, 첫 페이지는 가장 최근 20명이다. 남은 사용자는 다음 페이지에서 이어서 볼 수 있고, 다음 페이지에서는 이전 페이지로 돌아올 수 있어야 한다. 20명 이하면 다음 페이지는 없다. 다음 페이지가 없을 때 다음으로 이동하면 현재 페이지가 유지되어야 한다. ADMIN이 탈퇴 사용자 포함을 선택하면 그 조건으로 거른 뒤 같은 페이지 크기를 적용하고, WITHDRAWN의 탈퇴 시점도 보여 준다.
- **FR-019**: ADMIN은 검색어 하나로 사용자를 검색할 수 있어야 한다. 그 검색어는 아이디, 이름, 이메일 각각에 일부 일치로 비교하고, 하나라도 일치하면 결과에 포함한다. 일부 일치란 검색어가 그 값 안에 연속으로 포함되는 것이다. 세 항목이 모두 일치할 필요는 없다. 비교는 대소문자를 구분하지 않는다. 기본 검색은 WITHDRAWN을 제외한다. 탈퇴 사용자 포함을 선택하면 WITHDRAWN도 검색한다. 빈 검색어는 같은 조건의 목록과 같은 결과를 반환한다. 일치 항목이 없으면 빈 결과를 반환한다. 결과는 최근 가입 순이며, 페이지 크기는 FR-018과 같다.
- **FR-020**: ADMIN은 사용자 상세에서 아이디, 이름, 이메일, 권한, 상태를 볼 수 있어야 한다. 상태가 WITHDRAWN이면 탈퇴 시점도 볼 수 있어야 한다. 비밀번호는 포함하지 않는다. WITHDRAWN 사용자 상세는 아이디를 지정한 이력 확인으로 조회할 수 있어야 한다.
- **FR-021**: ADMIN은 ACTIVE와 INACTIVE 사이에서 사용자 상태를 바꿀 수 있어야 한다. INACTIVE 사용자는 로그인할 수 없고, 다시 ACTIVE가 되면 로그인할 수 있어야 한다. INACTIVE로 바뀌면 그 사용자의 진행 중인 모든 로그인 상태는 즉시 끝나야 하고, 이후 보호 기능은 다시 로그인을 요구해야 한다. WITHDRAWN으로의 변경과 WITHDRAWN 사용자의 상태 변경은 거부해야 한다.
- **FR-022**: ADMIN은 USER와 ADMIN 사이에서 사용자 권한을 바꿀 수 있어야 한다. 이미 로그인된 사용자를 포함해 다음 보호 기능부터 새 권한의 기능만 사용할 수 있어야 한다. 권한 변경만으로 로그인 상태가 끝나서는 안 된다. WITHDRAWN 사용자의 권한 변경은 거부해야 한다.
- **FR-023**: 시스템은 ACTIVE이면서 ADMIN인 계정을 최소 한 명 유지해야 한다. 마지막 ACTIVE ADMIN의 권한을 USER로 바꾸거나, 상태를 INACTIVE로 바꾸거나, 그 계정을 탈퇴시키는 요청은 거부해야 한다.
- **FR-024**: 회원탈퇴와 다른 어떤 기능도 사용자 기록을 물리적으로 삭제하지 않아야 한다.
- **FR-025**: ADMIN은 자신의 계정에 대해 회원정보 조회, 이름·이메일 수정, 비밀번호 변경, 회원탈퇴를 사용할 수 있어야 한다. 탈퇴는 FR-023을 따른다.
- **FR-026**: 사용 시작 시 아이디가 `admin`이고 권한이 ADMIN, 상태가 ACTIVE인 계정이 이미 존재해야 한다. 이름과 이메일은 필드 규칙을 만족하는 값으로 함께 준비되어 있어야 한다. 이 계정은 공개 회원가입으로 만들지 않아야 한다. 비밀번호 원문은 명세에 적지 않으며, 시작 시점에 아이디 `admin`으로 로그인할 수 있는 비밀번호가 준비되어 있어야 한다.

권한별 허용 기능은 다음과 같다.

| 기능 | 비로그인 | USER | ADMIN |
| --- | --- | --- | --- |
| 회원가입 | 허용 | 해당 없음 | 해당 없음 |
| 로그인 | 허용 | 해당 없음 | 해당 없음 |
| 로그아웃 | 거부 | 허용 | 허용 |
| 자신의 회원정보 조회 | 거부 | 허용 | 허용 |
| 자신의 이름·이메일 수정 | 거부 | 허용 | 허용 |
| 비밀번호 변경 | 거부 | 자신의 계정만 | 자신의 계정만 |
| 회원탈퇴 | 거부 | 자신의 계정만 | 자신의 계정만, 마지막 ACTIVE ADMIN은 거부 |
| 사용자 목록 조회 | 거부 | 거부 | 허용 |
| 사용자 검색 | 거부 | 거부 | 허용 |
| 사용자 상세 조회 | 거부 | 자신의 조회만 허용, 타인 상세는 거부 | 허용 |
| 사용자 상태 변경 | 거부 | 거부 | ACTIVE와 INACTIVE 사이만 허용 |
| 사용자 권한 변경 | 거부 | 거부 | USER와 ADMIN 사이만 허용, WITHDRAWN은 거부 |

### Key Entities *(include if feature involves data)*

- **사용자**: 사용자 관리의 대상. 아이디, 비밀번호 보관값, 이름, 이메일, 권한, 상태, 가입 시점을 가진다. 상태가 WITHDRAWN이면 탈퇴 시점을 가진다. 아이디와 이메일은 각각 전체 사용자 안에서 유일하다.
- **권한**: 사용자가 쓸 수 있는 기능의 구분. 이 PoC의 값은 USER와 ADMIN이다.
- **상태**: 계정의 사용 가능 구분. ACTIVE는 로그인할 수 있다. INACTIVE는 기록이 유지되고 로그인할 수 없으며, 진행 중인 로그인 상태가 즉시 끝난다. ADMIN이 ACTIVE로 되돌릴 수 있다. WITHDRAWN은 본인 탈퇴로만 설정되고 로그인할 수 없으며 기록과 탈퇴 시점이 남는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 올바른 값을 아는 신규 사용자는 회원가입부터 로그인 완료까지 3분 안에 마칠 수 있다.
- **SC-002**: 기본 목록 대상이 100명일 때 관리자는 첫 페이지 20명을 3초 안에 볼 수 있고, 다음 페이지를 따라 100명 전체를 최근 가입 순으로 확인할 수 있다. 이름 일부 검색의 첫 페이지도 3초 안에 보인다.
- **SC-003**: 일반 사용자가 다른 사용자의 개인정보를 조회하거나 수정하는 시도는 100% 거부되고, 대상 정보는 반환되지 않는다.
- **SC-004**: WITHDRAWN 사용자의 로그인 시도는 100% 실패하고, 해당 사용자 기록과 탈퇴 시점은 조회 가능한 상태로 남는다.
- **SC-005**: 이미 있는 아이디 또는 이메일로 하는 회원가입은 100% 거부되고 새 계정이 만들어지지 않는다. WITHDRAWN 기록의 아이디와 이메일도 포함한다.
- **SC-006**: 일반 사용자 기능 7개와 관리자 기능 5개는 각각 하나 이상의 성공 시나리오와 하나 이상의 거부 시나리오를 가진다.
- **SC-007**: 모든 인수 시나리오는 하나 이상의 FR 식별자를 인용한다. 검토자는 시나리오에서 해당 FR로, FR에서 해당 시나리오로 이동할 수 있다.
- **SC-008**: 위 결과가 충족되면 화면의 시각 디자인 완성도와 관계없이 이 PoC의 기능 검증은 성공이다.

## Assumptions

- 공개 회원가입은 USER/ACTIVE 계정만 만든다. 사용 시작 시 아이디 `admin`인 ACTIVE ADMIN이 이미 있으며, 세부 값은 FR-026을 따른다.
- ADMIN은 관리자 기능에 더해 자신의 계정에 대한 일반 사용자 본인 기능을 사용할 수 있다.
- 관리자는 다른 사용자의 이름, 이메일, 비밀번호를 수정하지 않는다. 관리자가 바꾸는 항목은 상태와 권한뿐이다.
- 비밀번호 찾기를 위한 이메일 발송, 이메일 소유 확인, 소셜 로그인은 이번 범위에 포함하지 않는다.
- 관리자의 대리 회원가입, 탈퇴 계정의 복구, 사용자 기록의 물리 삭제는 이번 범위에 포함하지 않는다.
- 권한은 USER와 ADMIN만 사용한다. 상태는 ACTIVE, INACTIVE, WITHDRAWN만 사용한다.
- WITHDRAWN은 본인 탈퇴로만 설정된다. 관리자의 상태 변경 값으로 WITHDRAWN을 선택할 수 없다.
- 기본 관리자 목록과 검색은 탈퇴 사용자를 제외한다. 탈퇴 이력은 포함 옵션 또는 아이디를 지정한 상세 조회로 확인한다. 검색은 검색어 하나이며, 아이디·이름·이메일 중 하나라도 검색어를 연속으로 포함하면 결과에 넣는다. 목록과 검색은 최근 가입 순으로 한 페이지에 최대 20명이고, 남은 결과는 다음 페이지에서 이어서 본다.
- 입력 검사에서 여러 항목이 실패하면 실패 이유를 한 결과에 모두 알려 주고, 통과한 항목만 따로 저장하지 않는다.
- 탈퇴 후에도 아이디와 이메일은 재사용할 수 없다.
- 목록의 기본 정렬은 최근 가입 순이다. 이 순서는 페이지를 넘겨도 유지되며, 첫 페이지가 가장 최근 가입자이다.
- 로그인 상태는 로그아웃, 본인 탈퇴, 또는 상태가 INACTIVE로 바뀔 때 끝난다. 권한 변경은 로그인 상태를 유지한 채 다음 보호 기능부터 적용된다. 별도의 자동 만료 시간은 이번 범위에서 정하지 않는다.
- 이번 PoC의 완료 판단은 화면 시각 품질이 아니라 위 기능 결과와, 요구사항(FR)에서 인수 시나리오와 이후 테스트로 이어지는 추적성이다.
