# 사용자 관리 PoC Constitution

본 프로젝트는 SI/SM 환경에서 Spec-Driven Development(SDD) 적용 가능성을
검증하기 위한 사용자 관리 프로그램 PoC이다. 이 헌법은 해당 범위의
요구사항, Spec, 설계, 구현, 테스트에 우선한다.

## Core Principles

### I. Spec 우선

구현보다 요구사항과 Spec 정의를 우선한다.

- 기능 구현은 해당 기능의 Spec이 작성된 뒤에만 시작한다.
- Spec에 정의되지 않은 동작은 구현하지 않는다. 동작이 필요하면 Spec을 먼저 개정한다.
- 구현 중 발견된 요구 변경은 코드에 먼저 반영하지 않고 Spec 변경으로 기록한다.

**Rationale**: 이 PoC의 목적은 코드 산출이 아니라 SDD 적용 가능성을 검증하는 것이다.
Spec이 구현보다 뒤처지면 요구사항과 동작의 추적성이 성립하지 않는다.

### II. 산출물 추적성

요구사항, Spec, 설계, 구현, 테스트 사이의 추적 연결을 유지한다.

- 각 구현 단위는 대응하는 Spec 항목을 식별할 수 있어야 한다.
- 각 테스트는 검증하는 Spec 항목 또는 요구사항을 식별할 수 있어야 한다.
- 상위 산출물과 연결되지 않은 구현이나 테스트는 완료로 간주하지 않는다.

**Rationale**: SI/SM에서 변경 영향과 검증 범위는 산출물 간 연결로 설명되어야 한다.

### III. 입력값 검증

모든 사용자 입력값을 처리 전에 검증한다.

- 형식, 길이, 허용 값, 필수 여부를 Spec에 정의하고, 그 규칙으로 검증한다.
- 검증에 실패한 입력은 거부하고, 호출자가 구분할 수 있는 실패 결과를 반환한다.
- 클라이언트 측 검증만으로 이 원칙을 충족했다고 보지 않는다. 신뢰 경계의 서버 측 검증을 수행한다.

**Rationale**: 미검증 입력은 데이터 오염과 권한 우회의 공통 원인이다.

### IV. 비밀번호 비평문 저장

비밀번호는 평문으로 저장하지 않는다.

- 저장 값은 솔트를 포함한 일방향 비밀번호 해시, 또는 그와 동등한 비밀번호 해싱 결과여야 한다.
- 비밀번호 검증은 저장된 해시에 대한 비교로만 수행한다.
- 비밀번호 평문을 로그, 응답 본문, 오류 메시지, 산출물에 남기지 않는다.
- 가역 암호만으로 비밀번호를 저장하는 방식은 이 원칙을 충족하지 않는다.

**Rationale**: 저장소나 로그가 유출되어도 비밀번호 원문이 노출되지 않아야 한다.

### V. 역할 분리

일반 사용자와 관리자 권한을 구분한다.

- 보호되는 기능은 허용 역할을 Spec에 명시한다.
- 요청마다 인증된 역할이 해당 기능을 허용하는지 검사한다.
- 허용되지 않은 역할의 요청은 거부한다.

**Rationale**: 사용자 관리 기능은 역할에 따라 허용 범위가 달라지며, 구분되지 않은 권한은
개인정보 격리 원칙을 무력화한다.

### VI. 개인정보 격리

일반 사용자는 다른 사용자의 개인정보를 조회하거나 수정할 수 없다.

- 일반 사용자의 조회·수정 범위는 자신의 계정으로 제한한다.
- 다른 사용자의 개인정보에 대한 접근은 관리자 역할과 Spec에 정의된 목적으로 한정한다.
- 식별자 변경만으로 타인 데이터에 접근하는 요청은 거부한다.

**Rationale**: 수평적 권한 상승을 막아 계정 단위로 개인정보를 격리한다.

### VII. 회원탈퇴 Soft Delete

회원탈퇴는 Soft Delete로 처리한다.

- 탈퇴 시 사용자 레코드를 물리 삭제하지 않고, 탈퇴 상태와 탈퇴 시점을 기록한다.
- 탈퇴한 계정은 일반 인증과 일반 조회 대상에서 제외한다.
- 물리 삭제는 이 원칙을 개정하기 전에는 수행하지 않는다.

**Rationale**: 탈퇴 이력은 감사와 변경 추적에 필요하며, 물리 삭제는 그 이력을 제거한다.

### VIII. 주요 기능 테스트

주요 기능에는 테스트를 작성한다.

- 주요 기능은 Spec에 사용자 목표로 정의된 기능이다.
- 각 주요 기능은 성공 경로와, Spec에 명시된 거부 경로를 검증하는 테스트를 가진다.
- 해당 테스트가 없는 주요 기능은 완료로 간주하지 않는다.

**Rationale**: 요구사항이 동작으로 확인되어야 SDD 적용 여부를 판단할 수 있다.

### IX. 회귀 검증

기존 기능에 영향을 주는 변경은 회귀 테스트로 검증한다.

- 영향 받는 기존 테스트가 있으면 변경 후 그 테스트를 다시 실행하고 통과를 확인한다.
- 영향 받는 기존 동작에 테스트가 없으면, 회귀 테스트를 추가한 뒤 통과를 확인한다.
- 기존 동작의 계약이 바뀌면 Spec을 먼저 개정하고, 영향 받는 테스트를 그 Spec에 맞게 갱신한다.

**Rationale**: 이후 변경이 이미 합의된 Spec 준수를 깨지 않음을 확인해야 한다.

### X. SI/SM 산출물·변경 추적

SI/SM 산출물 관리와 변경 추적에 재사용할 수 있는 구조를 유지한다.

- Spec, 설계, 작업, 테스트 산출물은 기능 단위로 식별되고 서로 연결되어야 한다.
- 변경은 어떤 요구사항 또는 Spec 항목을 바꾸는지 남겨야 한다.
- 산출물 경로와 식별자는 후속 변경에서 같은 항목을 다시 찾을 수 있어야 한다.

**Rationale**: 이 PoC는 일회성 화면 구현이 아니라, 이후 산출물 관리와 변경 추적에
쓸 수 있는 SDD 구조를 검증한다.

## 보안 및 데이터 처리 제약

원칙 III–VII의 준수 여부는 아래 조건으로 판단한다.

- 사용자 입력의 검증 규칙은 Spec에 적고, API 또는 동등한 신뢰 경계에서 적용한다.
- 비밀번호 저장 컬럼과 로그에는 평문 비밀번호가 존재하지 않아야 한다.
- 역할은 최소 `일반 사용자`와 `관리자`를 구분한다. 역할이 확인되지 않은 보호 요청은 거부한다.
- 일반 사용자 API는 대상 사용자가 요청자 자신인지 확인한 뒤에만 개인정보를 반환하거나 수정한다.
- 탈퇴 처리된 사용자는 삭제 표시와 시점을 유지한 채 남고, 인증·일반 목록·일반 상세 조회에서 제외된다.

## 품질 게이트와 산출물 추적

작업은 요구사항 정의, Spec, 설계, 작업 분해, 구현, 테스트 순서로 진행한다.

- Spec 항목이 없는 구현 작업은 시작하지 않는다.
- 완료는 Spec 항목, 구현, 테스트가 연결되고 관련 테스트가 통과한 상태로 판단한다.
- 기존 기능의 동작이나 계약을 바꾸는 변경은 원칙 IX에 따라 회귀 테스트를 통과해야 한다.
- 기능별 Spec, 계획, 작업, 테스트를 변경 추적의 기준 산출물로 사용한다.

## Governance

이 헌법은 본 PoC의 다른 로컬 관행보다 우선한다. 헌법과 충돌하는 구현, 테스트 생략,
추적 불가능한 변경은 허용하지 않는다.

개정 절차:

1. 변경 이유, 영향 받는 원칙, 기존 산출물에 대한 영향을 기록한다.
2. 아래 버전 정책에 따라 헌법을 개정한다.
3. 개정일과 본 파일 상단의 Sync Impact Report를 함께 갱신한다.
4. 영향을 받는 Spec, 계획, 작업을 후속 변경으로 식별한다.

버전 정책:

- MAJOR: 원칙의 삭제, 또는 기존 원칙의 하위 호환되지 않는 재정의.
- MINOR: 새 원칙이나 섹션의 추가, 또는 지침의 실질적 확장.
- PATCH: 의미 변화가 없는 문구 정리, 오탈자 수정, 명확화.

준수 검토:

- Spec, 계획, 작업, 구현, 테스트 검토 시 관련 원칙의 위반 여부를 확인한다.
- 원칙과 맞지 않는 작업은 예외로 진행하지 않는다. 원칙 변경이 필요하면 헌법을 먼저 개정한다.
- 런타임 개발 지침은 기능별 Spec, 계획, 작업 산출물을 따른다.
